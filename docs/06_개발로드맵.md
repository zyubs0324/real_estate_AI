## 전체 구조

```
Phase 1  기반 구축 (필수 선행)
```

  - **등기부 API 비용·한도 정책**
    - Quick Check는 등기정보광장 API(무료, 하루 1,000건 한도) 우선 사용
    - 자동실행은 신규 등록 시 1회만 (이후 재조회는 정기 재진단 주기 설정 따름)
    - 한도 초과 또는 더 상세한 데이터 필요 시 CODEF API로 전환 (건당 50~100원)
    - 소규모 사무소(월 등록 100건 미만) 기준 등기정보광장 무료 한도로 충분

- [ ] **구성원 초대 플로우 (Supabase `inviteUserByEmail`)**

### 3-D-1. 타부동산 관리
- [ ] **타부동산 목록** — 거래 이력이 있는 타부동산 사무소 조회·관리

  - 검색: 상호명, 대표자명, 전화번호
- [ ] **타부동산 등록 — 자동 조회 우선 플로우**
  - 상호명 또는 중개사무소 등록번호 입력 → [자동 조회] 버튼
  - **부동산중개업 정보 서비스 API** (data.go.kr, 무료) 호출 → 일치 업체 목록 반환
  - 목록에서 선택 시 폼 자동 채움: 상호명, 대표 공인중개사명, 전화번호, 사무소 주소, 등록번호
  - 조회 불가·미검색 시 수동 직접 입력으로 전환 (모든 필드 직접 입력)
  - **저장 후 즉시: "개업공인중개사 정보를 등록하시겠습니까?" 프롬프트**
    - [예]: 인물 등록 폼으로 이동, 소속(삼성부동산) + 역할(대표중개사) 자동 지정, 이름은 API 조회값 자동 채움
    - [나중에]: 건너뜀 — 타부동산 상세 페이지에서 언제든 추가 가능
    - 이유: 부동산은 개업공인중개사가 반드시 있어야 하므로, 등록 즉시 연결하는 것이 자연스러운 흐름
- [ ] **타부동산 상세 페이지**
  - 기본 정보 (상호명·대표·전화·주소·등록번호)
  - **구성원 목록** — agency_id로 연결된 people 리스트 (역할 포함)
    - **[+ 구성원 등록] 버튼**: 인물 등록 폼으로 이동, 소속(해당 타부동산) 자동 지정
      - 인물 폼에서 소속이 자동 선택된 상태로 이름·전화번호·역할만 입력
      - 역할 선택: 대표중개사 / 소속공인중개사 / 중개보조원
    - **기존 인물 연결**: 인물 검색 → 소속 지정 (이미 등록된 사람을 타부동산 소속으로 변경)
    - 구성원 목록: 이름, 역할, 전화번호, 담당 거래 건수
  - **거래 이력** — 이 타부동산과 공동중개한 거래 전체 목록 (co_agency_id 기준)
    - 주소, 거래 유형, 담당 직원(co_agent_id), 계약일, 거래금액
    - 클릭 시 해당 거래 상세로 이동
  - **수집 매물** — 이 타부동산이 등록한 외부 수집 매물 (listing_agency_id 기준)
    - 주소, 거래 유형, 현재 상태 표시
  - **메모** — 타부동산 단위 메모 (예: "소장 김철수 — 수수료 협의 까다로움")
    - `agencies.notes` 필드에 저장 (단순 메모) 또는 memos 테이블 확장 방식 구현 시 판단
- [ ] **타부동산 자동 연결** — 외부 매물 수집 시 담당 부동산 식별·연결
  - **플랫폼 추출 정보 활용**: 네이버·직방 등 외부 매물에는 등록 중개사무소명·등록번호가 표시됨
    - Playwright 추출 시 이 정보도 함께 추출 시도
    - 추출된 상호명 또는 등록번호로 `agencies` 테이블 검색 → 일치 시 listing_agency_id 자동 연결
    - 미등록 타부동산이면: "삼성부동산(미등록)이 확인됩니다. 등록하시겠습니까?" 안내 → 인라인 등록 가능
  - 외부 매물 수집 폼의 "담당 타부동산" 선택 필드 → 수동 선택도 항상 가능
  - listing_agency_id + listing_agent_id 저장 → 타부동산 상세의 "수집 매물" 목록 자동 연결

### 3-E. 거래 정보 관리
- [ ] **빠른 등록 플로우** — 주소 검색 → [우리매물로 등록] 클릭 → 슬라이드 패널에서 연속 처리
  - 매도인(임대인) 인물 연결 → 거래 유형 선택 → 희망가 입력 → 상태 선택(매도의뢰/임대의뢰)
  - 건물 유형 선택 (lookup_codes 기반 드롭다운, Quick Check 결과로 자동 채워질 수 있음)
  - 등록 완료 시 `properties` 레코드 + `transactions` 레코드 동시 생성
  - **"매도의뢰 등록 = 거래 생성"**: 희망가(`transactions.price`)는 거래에 저장, properties에 별도 가격 필드 불필요
  - **등록 직후 Quick Check 자동 실행** (백그라운드): 건축물대장(건물 유형 포함) + 등기부 + 규제지역 조회 → property_diagnostics 저장 + building_type 자동 갱신 → 리스트 태그 즉시 갱신
- [ ] **외부 매물 수집** (외부 플랫폼 URL 붙여넣기 → 자동 정보 추출 → 관심 매물 등록)
  - **진입점**: 대시보드 검색창 옆 [외부 매물 수집] 버튼 → URL 입력 페이지로 이동
  - URL 입력 → Playwright 렌더링 → 매물 정보 자동 추출 → 미리보기 폼 → [관심 매물로 저장]
  - **지원 플랫폼 및 고유 ID 추출 방식** (`lib/external-extractor.ts`):
    | 플랫폼 | URL 예시 | 고유 ID 추출 |
    |---|---|---|
    | 네이버(new) | `new.land.naver.com/complexes/ID?articleNo=X` | 쿼리파라미터 `articleNo` |
    | 네이버(fin) | `fin.land.naver.com/map?layer=인코딩값` | Playwright 렌더링 후 DOM |
    | 네이버(구형) | `land.naver.com/article/info?articleNo=X` | 쿼리파라미터 `articleNo` |
    | 직방 | `zigbang.com/home/apt/item-catalog?areaHoId=X` | 쿼리파라미터 `areaHoId` |
    | 다방 | `dabangapp.com/map/apt?detail_id=X` | 쿼리파라미터 `detail_id` |
    | 피터팬 | `peterpanz.com/house/ID` | URL 경로의 마지막 세그먼트 |
  - **중복 감지 및 처리** (`external_ids JSONB` 기반):
    - 1단계: 동일 플랫폼 동일 ID → "이미 등록된 매물" → [기존 매물 보기] / [병합] / [신규 등록]
    - 2단계: 다른 플랫폼이지만 주소+호수 일치 → "같은 주소의 매물이 존재합니다" → 동일 선택
    - 병합: 기존 레코드에 새 플랫폼 ID·URL 추가 (external_ids에 추가)
    - 신규: 별도 레코드 생성 (의도적으로 다른 매물인 경우)
  - **자동 추출 필드**: 건물명, 건물 유형, 보증금, 월세, 전용면적, 층수, 법정동 주소
    - 호수: 플랫폼이 의도적으로 숨김 → 중개사가 직접 입력
    - 주소 정규화: 추출된 건물명 → 도로명주소 API로 표준 주소 변환 시도
  - 추출 실패(페이지 구조 변경·봇 차단 등) 시 → 빈 폼으로 수동 입력 전환 (URL은 source_url 자동 저장)
  - **담당 타부동산 지정** (선택): 매물을 외부에 등록한 타부동산과 담당 직원 연결
    - listing_agency_id + listing_agent_id 저장 → 타부동산 상세의 "수집 매물" 목록에 자동 표시
    - 타부동산 미등록 시 인라인 신규 등록 후 연결 가능
  - 등록 후 Quick Check 자동 실행 (위반건축물·등기 이상 즉시 확인)
  - 리스트에서 출처 플랫폼 뱃지 표시 (`네이버` / `직방` / `다방` / `피터팬`), [원본 링크] 버튼 제공
- [ ] **구글 시트 일괄 가져오기** (외부 매물 수집 페이지 내 별도 탭)
  - 구글 시트를 "링크 있는 사람 모두 보기"로 공개 후 URL 입력 → 전체 데이터 일괄 등록

    - Playwright 불필요 (단순 HTTP 요청) — 네이버·직방보다 훨씬 간단

    - 매핑 설정 저장 → 같은 형식의 시트를 나중에 다시 가져올 때 재사용
    - 미리보기: 매핑 후 첫 5행 확인 → [가져오기 시작]
  - **주소 정규화**: 각 행의 주소를 도로명주소 API로 표준화 (배치 처리, rate-limited)
  - **중복 감지**: (도로명주소 + 호수) 기준으로 기존 등록 매물과 대조
    - 중복 발견 시: 건너뜀(skip) + 결과 요약에 포함
  - **완료 요약**: `N건 성공 / M건 중복 건너뜀 / K건 실패(주소 인식 불가)` 표시
    - 실패 목록 CSV 다운로드 제공 (주소 수정 후 재시도 가능)
  - **Quick Check 일별 분산 예약** (1,000건 이상 시 당일 API 한도 초과 방지)
    - 등기정보광장 하루 1,000건 한도 → 가져오기와 동시에 전부 실행하지 않음
    - 하루 최대 800건씩 백그라운드 자동 실행 (나머지 200건은 일상 사용 예비)
    - admin 화면에서 "Quick Check 예약 현황" 진행률 확인 가능
- [ ] **구글 시트 실시간 동기화** (단방향: 시트 → 시스템, 시트는 절대 수정하지 않음)

    - 시트는 "링크 있는 사람 모두 보기"로 공개 유지 (읽기 전용)
  - **매칭 키**: (도로명주소 + 호수) 조합 → 시트에 "시스템ID" 컬럼 존재 시 우선 사용
  - **변경 유형별 처리**:
    - 새 행 추가 → 관심 매물로 신규 등록
    - 기존 행 수정 → 해당 매물 정보 업데이트 (변경 로그 기록)
    - 행 삭제 → **자동 삭제 안 함** → `sheet_deleted` 플래그 설정 + admin 검토 대기
  - **동기화 변경 로그** (`sync_logs` 테이블): 매 동기화마다 변경 내역(추가/수정/삭제플래그) 영구 기록
  - admin 화면: 마지막 동기화 시간, 변경 건수, 검토 대기 목록, 수동 동기화 실행 버튼
  - **자동 백업 전략** (3단계 계층형 보존, Supabase Storage에 저장):

    |---|---|---|
    | 동기화 전 스냅샷 | 매 동기화 직전 자동 실행 | 최근 10회분 |
    | 일별 백업 | 매일 새벽 | 30일 |
    | 월별 백업 | 매월 1일 | 12개월 |
    - 스냅샷 총 52개 이하, 일별 방식 대비 동일 저장공간 + 12배 긴 복구 범위
    - 나쁜 동기화 직후 즉시 롤백: 스냅샷 선택 → [이 시점으로 복구] 버튼
    - `sync_logs`의 변경 로그로 무엇이 언제 바뀌었는지 상세 감사 가능
- [ ] **DB 복구 페이지** (admin 전용 — GitHub 커밋 히스토리 UI 차용)
  - **백업 목록** (시간순 역정렬, 타입별 컬러 아이콘):

  - **각 항목 표시**: 날짜·시간, 자동 생성 코멘트, 매물 수, 파일 크기, [이 버전으로 복구] 버튼
    - 코멘트 예시: `구글 시트 동기화 전 스냅샷 · 23건 변경 감지`
    - 코멘트 예시: `외부 매물 수집 · 네이버 옥수 삼성아파트 101동`
    - 코멘트 예시: `복구 전 자동 백업 · 2025-04-28 03:00 버전으로 복구`
  - **[수동 백업 생성] 버튼**: 언제든 현재 상태를 즉시 백업
  - **복구 실행 흐름**:
    1. [이 버전으로 복구] 클릭
    2. 확인 모달: "현재 데이터는 덮어씌워집니다. 진행 전 현재 상태를 자동 백업합니다"
    3. 현재 상태 자동 백업 생성 (`pre_recovery` 타입)
    4. 선택한 스냅샷으로 복구 실행
    5. 완료 메시지 + 복구된 버전 정보 표시

  - 이전 거래 선택 시: `parent_transaction_id` FK 자동 저장 + 이전 거래 참여자 자동 불러오기 제안
  - **갱신청구권 소진 자동 감지**: parent chain에서 `is_renewal_right_used=true` 존재 시

- [ ] 거래 참여자 등록 (transaction_participants — 역할별 다자간, 지분 비율, 활성/예비/제외 상태 포함)

  - 거래 메인 화면: 활성만 표시 / 예비는 "예비 후보" 섹션에 접어서 표시
  - 알림·연락: 활성 참여자에게만 발송
- [ ] **납부 단계 관리** (transaction_payments)

    - 매매: 계약금의계약금 → 계약금(잔액) → 중도금(optional) → 잔금
    - 임대차: 계약금의계약금(optional, 직접 추가) → 계약금(잔액) → 잔금(보증금 잔액)
    - 임대차도 계약 전 계약금의계약금 발생 가능 (가계약금) → 직접 추가 버튼으로 삽입
    - 예: 보증금 5천만원, 계약금 10% → 계약금의계약금 50만원 + 계약금 잔액 450만원 + 잔금 4,500만원

  - 각 항목: 금액, 예정일, 실제 납부일, 납부 완료 여부
  - **납부 단계별 이체확인증 첨부** (`attachments`, entity_type=transaction_payment)

### 3-G. 전체 매물 리스트 + 주소 검색
- [ ] 전체 매물 리스트 화면
- [ ] **매물 라벨 필터** (상단 탭, 복수 선택 가능): [전체] [우리 매물] [관심 매물] [집중 관리]
- [ ] 필터
  - 기본: 주소(동·구), 거래 유형(매매/전세/월세), 거래 상태, 담당 구성원, 위험도(없음/주의/위험)
  - 매물 속성: **건물 유형** (lookup_codes 기반 — 아파트/오피스텔/다세대 등, 복수 선택)
  - 가격 조건: **보증금 범위** (최소~최대, transactions.price 기준) / **월세 범위** (최소~최대, transactions.monthly_rent 기준)
  - 기타: 인물, 규제지역, 비표준 수수료(is_custom_commission), 수수료 미수령(commission_is_paid=false)
  - **고객 관심 필터**: 특정 고객(person)을 선택하면 해당 고객이 관심 표시한 매물만 조회
    - [전체] [좋아요] [관심] [봤음] [계약의향] 탭으로 세분화
    - 고객 선택 → 리스트가 해당 고객의 property_interests 기준으로 필터·정렬 (좋아요 상단)
  - **매물 출처** (external_ids JSONB 키 기반 필터, 복수 선택 가능):
    - [전체]
    - [우리 매물] — is_our_property=true (외부 플랫폼 동시 등록 여부 무관)
    - [직접 등록 관심 매물] — is_watchlist=true, external_ids='{}' (외부 수집 없이 직접 등록한 매물)
    - [네이버] — external_ids ? 'naver'
    - [직방] — external_ids ? 'zigbang'
    - [다방] — external_ids ? 'dabang'
    - [피터팬] — external_ids ? 'peterpan'
    - [구글 시트] — external_ids ? 'sheet'
    - 복수 플랫폼 등록 매물(네이버+직방 동시)은 해당 필터 모두에 포함됨
- [ ] **리스트 위험 태그 표시** (property_diagnostics 캐시 기반, 클릭 전 즉시 확인)
  - **위험도 컬러 배지**: 🟢 없음 / 🟡 주의 / 🔴 위험 (risk_level 기반)
  - **항목별 텍스트 태그**: 해당 항목만 표시, 없으면 태그 없음
    - `위반` (빨강) — has_violation_building
    - `근저당` (주황) — has_mortgage
    - `압류` (빨강) — has_seizure
    - `경매` (빨강) — has_auction
    - `가처분` (주황) — has_injunction
    - `신탁` (회색) — has_trust
    - `임차권등기` (주황) — has_lease_registration
    - `토지거래허가구역` (파랑) — is_land_transaction_zone
    - `재개발·재건축` (보라) — is_redevelopment_zone
    - `투기과열` (파랑) — is_speculation_zone
  - 태그는 리스트 행에 인라인으로 표시 → 클릭 없이도 어떤 위험인지 즉시 파악 가능
  - "N일 전 진단" 타임스탬프 표시, 30일 초과 시 재진단 안내
  - **미진단 매물**: 회색 배지 "확인중" (등록 직후 Quick Check 실행 중) / "미진단" (오류 시)
- [ ] 정렬: 최근 등록순, 만료 임박순, 거래금액순
- [ ] 리스트 + 지도 뷰 전환

## 개발 우선순위 원칙

1. **Phase 1을 완전히 끝낸 뒤** Phase 2로 넘어간다. 특히 Supabase Auth와 주소 표준화 레이어는 이후 모든 기능의 기반.
2. **Phase 2 → Phase 3** 순서로 진행. AI 질의응답(Phase 4)보다 진단 리포트(Phase 2)와 CRM(Phase 3)을 먼저 완성한다.
3. 각 Phase 내 항목은 위에서 아래 순서로 구현한다.
4. API 연동 시 반드시 `.env.local`에서 키를 불러오고, 코드에 직접 삽입하지 않는다.
5. **Mock 우선 개발**: API 키 없는 초기 단계에서는 `NEXT_PUBLIC_USE_MOCK_API=true` + `lib/apis/__mocks__/`로 UI 먼저 완성. API 키 준비 후 실제 연동.
6. **소단위 육안 테스트**: 각 Unit(U1-1 ~ U5-4)은 브라우저에서 눈으로 결과를 확인할 수 있을 때만 완료로 처리. 자세한 Unit별 명세는 플랜 파일(`~/.claude/plans/ai-vast-nebula.md`) 참고.
